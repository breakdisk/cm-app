# Neighborhood Delivery Network, Phase 0: Decision Log

This file records the decisions taken while building Phase 0 (partner safety) of the Neighborhood Delivery Network on branch `feat/neighborhood/phase-0-partner-safety`. It is kept after the working ledger is deleted, so the reasoning survives the branch. The rollout steps live in `docs/runbooks/neighborhood-phase-0-rollout.md`.

Each decision shows only its final form. Where a later ruling reversed or amended an earlier one, one sentence says what it replaced and why. Reasons and costs are the ledger's own; where the ledger gave no cost it says "not recorded".

Terms used below: pid is the partner id claim carried in a partner-bound access token. POD is proof of delivery and POP is proof of pickup. AWB is the air waybill, the tracking number. SLA is service level agreement. RTL is right-to-left script. BFF is a portal's backend-for-frontend route. PIN is the one-time delivery code. RED means a test seen failing before the fix; GREEN means it then passes.

## 1. Decisions

### Process

- **Implementation runs on a cheaper model, task reviewers run on Sonnet (Opus for the dispatch close task, Task 0.12), and the final review runs on a fresh Opus reviewer; the executor switched from inline to subagent-driven for Tasks 0.11 to 0.16.** The user asked to use the right model to save tokens: Opus for orchestration, planning and design, Sonnet for implementers. *Cost if wrong:* weaker per-task judgement, caught by TDD (test-driven development) and the final review.
- **The scoped re-review of the fix wave (`e6ac2702..1b3cf4fd`) ran on Opus, not the cheaper tier.** Twice in the wave a fix introduced a HIGH-severity issue that only the automated security review caught, and this was the last gate before merge. *Cost if wrong:* more tokens than a Sonnet re-review.
- **Task 0.5 (backfill) accepted having no watched RED test.** The plan ordered script before test, but the committed test script then found a real bug (an `awk` `NR==FNR` idiom with an empty first file dropped every row), which was fixed and re-run green. *Cost if wrong:* none, the bug was fixed and is covered.
- **Task 0.12 (assignment close) accepted having no true RED test.** The implementer wrote code before tests ran, then mutation-tested: removing the open-task guard, the flag gate, and the `cancel_route` close each failed tests. *Cost if wrong:* a test that never failed for the right reason, mitigated by the mutations.
- **Fix every Important finding, minors M1 to M5, the POD cross-tenant read and the partner Orders page inside this branch, instead of gating them behind later flag flips.** The owner's standard is to remove a predictable blocker, not promise to remove it. *Cost if wrong:* a longer fix wave.
- **The fix wave ran as three groups by area (A identity/docs/config, B dispatch/order-intake/pod, C scanner/portal), with Group C allowed to run in parallel with Group B's correction round, committing by explicit path.** One agent across about ten services would exceed what it can hold. The file sets were disjoint and cargo serialises builds on its own lock. This replaced the first plan of strictly sequential groups. *Cost if wrong:* one commit picks up the other agent's staged file; both groups' commit file lists were checked before the re-review and showed no cross-group sweep.
- **Fix all minor residuals from the re-review now.** A doc comment that says "never block capture" over fail-closed code invites someone to "fix" it back. *Cost if wrong:* one small extra commit.

### Identity and tokens

- **A new error `AppError::PartnerContextRequired` (403, code `PARTNER_CONTEXT_REQUIRED`) was added to `libs/errors`.** `AppError::Forbidden` always reports the code `FORBIDDEN`, so it cannot carry this code; no other crate matches `AppError` exhaustively. *Cost if wrong:* one extra enum variant.
- **The membership upsert never reactivates a suspended membership; it answers 409.** The plan said create-or-reactivate, but a retried approval must not undo an admin suspension. *Cost if wrong:* reactivation needs a deliberate route, to be added when the store offboarding flow needs it.
- **Token issue fails the login when the membership lookup errors, rather than omitting pid as `features_for_tier` does.** An omitted pid is the wider, unscoped token for a partner user. *Cost if wrong:* login is unavailable while the identity database is unreadable, which already breaks login.
- **`services/identity/tests/integration/mod.rs` was left untouched** even though `AuthService::new` and `AppState` gained fields. It is not a compiled target and already had 11 errors before this branch. *Cost if wrong:* the suite already needs repair when someone wires it.
- **A user whose membership rows are all `suspended` is refused a token (403 `PARTNER_MEMBERSHIP_INACTIVE`) at all four issue sites; suspension takes effect at the next refresh.** Fail closed is the safe default for a former store rider. Token refusal is tested at unit and repository level plus a source guard, because there is no `AuthService` test harness. *Cost if wrong:* a former store rider cannot log in until an admin clears the membership, which is recoverable.
- **The internal membership upsert refuses users whose roles fall outside `partner`, `store_manager`, `store_clerk` and `driver`, and also returns 404 for an unknown or foreign-tenant `user_id`.** The carrier-in-tenant check stays with the mesh caller because identity cannot read the carrier database. The 404 goes beyond the ruling and was accepted as fail closed. *Cost if wrong:* not recorded.

### Backfill

- **Rider backfill (`driver_ops.drivers.carrier_id`) is opt-in through `--riders`, default off.** Backfilling existing third-party-carrier riders changes their token scope, and Phase 0 only needs partner-portal users. *Cost if wrong:* an existing carrier rider has no pid until `--riders` is run or the rider is re-created.
- **The membership backfill gained `TENANT_ID` filtering and a committed, repeatable test script** (`scripts/backfill/test-partner-memberships.sh`); the plan only asked for a manual disposable-database test. *Cost if wrong:* not recorded.
- **The shipment-link backfill does not check that the shipment still exists.** A link to a missing shipment is never read. *Cost if wrong:* a few orphan link rows.

### Order-intake scoping

- **Dispatch resolves the driver's carrier through a new `DriverAvailabilityRepository::carrier_id` with a default body returning `None`; a failed lookup logs and does not stop assignment.** The default keeps every existing test double compiling and treats a platform driver as linking nothing. *Cost if wrong:* a carrier task whose lookup failed is not linked until `partner-shipment-links.sh` runs.
- **`ShipmentRepository::is_linked` has a default body returning `false`; the Postgres implementation overrides it.** Any test double fails closed. *Cost if wrong:* not recorded.
- **Partner scope is passed to `ShipmentQueryService::list` and `get_for` as an explicit `PartnerAccess` argument instead of a `partner_id` on `Actor`.** `Actor` literals appear in 8 tests and the cancel authority code, which does not need partner scope. *Cost if wrong:* none, same enforcement.
- **Partner scope is an extra AND on top of the owner and tenant rules.** A pid-bound merchant would lose sight of its own bookings that are not linked to its partner; no such token exists today. *Cost if wrong:* revisit when a user is both merchant and partner.
- **order-intake `GET /v1/shipments/:id/events` now goes through `get_for`.** It checked tenant only, so any merchant, customer or partner could read any shipment timeline by id, a live cross-merchant leak (RED test first, 500 then 404). *Cost if wrong:* not recorded.

### Driver-ops and hub-ops

- **The manifest and roster endpoints require a permission of scoped tokens too** (`FLEET_READ`, `CARRIERS_MANAGE`, `CARRIERS_MANAGE_OWN` or `STORE_RIDERS_MANAGE`); the plan said pid alone suffices. This refuses a store rider (driver role plus pid). An unscoped partner-role user without pid keeps `CARRIERS_MANAGE_OWN` access until enforcement so the partner portal does not break during the backfill window. *Cost if wrong:* in that window an unscoped partner can still name another carrier on the manifest, the exposure that exists today and that enforcement removes.
- **The hub-ops AWB lookup guard is verified by a source-scan test.** The handler needs a database and the bootstrap `AppState` is not constructible in tests. *Cost if wrong:* a refactor that moves the call but keeps the string could fool the test.
- **Task 0.10 went beyond the plan and added `require_unscoped` to 11 hub-ops reads plus `get_induction`, dispatch `get_route` and `list_routes` (stops carry recipient addresses), and delivery-experience `get_by_shipment_id` and `list_shipments` (tenant-wide tracking including driver phone).** The survey found handlers the plan did not list. *Cost if wrong:* a pid-bound token loses access to those; none of the three portals call them for a partner (checked).
- **The hub-ops POP gate change stays in and is recorded in the runbook as a behaviour change at deploy.** The `pop-status` call returned 400 on every request, so the gate failed closed with a 500; it now evaluates. A gate that always errors is not a gate. *Cost if wrong:* container assignments blocked by the 500 start passing where POP is complete, and fail with a clear message where it is not.

### Payments and analytics

- **Wallet, invoice and analytics handlers get `require_unscoped` but no per-handler tests.** Payments and analytics have no router or `AppState` test harness. The shared helper is unit-tested in `libs/auth`, the role removal has RED to GREEN tests, and the Task 0.10 inventory script enforces the guard on each handler. *Cost if wrong:* a handler could lose its guard until 0.10 landed; 0.10 was the next task.
- **The partner dashboard (not only payouts and SLA, as the plan listed) was rewritten.** Its earnings tiles, top-zones table (the whole dispatch queue) and SLA trend were built from tenant-wide endpoints. The Pending Remittance card and Payout Summary were removed; zones now come from `sla-summary` and the trend from `sla-history`. *Cost if wrong:* partners lose a tile that showed the tenant's money.
- **`apps/partner-portal/src/lib/api/payments.ts` was deleted and `jest.config.mjs` added.** Only payouts used the file; `npm test` ran jest with no config, so no TypeScript test could run. The config uses relative `testMatch` globs and `@jest/globals` imports, avoiding an `@types/jest` dependency. *Cost if wrong:* not recorded.

### Dispatch assignment close

- **An unknown assignment status parses to Cancelled with an error log, not Pending.** The old "unknown maps to Pending" constraint describes old images, which is why readers ship first. An unknown status mapped to Cancelled must never be written back by a save or update path. *Cost if wrong:* a row with a future status could be rewritten to cancelled.
- **The close consumer resolves routes by shipment (`route_stops` or `driver_ops.tasks`), never by the event's `driver_id`.** The ADR-0015 split between `drivers.id` and `user_id` makes the event driver id unreliable. *Cost if wrong:* none if resolved by shipment.
- **The consumer reads the outcome topics through a local lenient struct `{task_id: Option, shipment_id}`, resolving the route by `driver_ops.tasks.id = task_id` with a fallback by shipment.** The topics actually carry driver-ops `TaskCompleted` and `TaskFailed`, not the `DeliveryCompleted` struct. *Cost if wrong:* none, both keys are present.
- **`cancel_route` closes its assignment as `cancelled`, so that path is not behind `DISPATCH__CLOSE_ASSIGNMENTS`; only `completed` writes (consumer and sweep repair) are flag-gated.** `cancelled` is an existing value old images read. *Cost if wrong:* none for old readers.
- **A finished route closes any active assignment (pending or accepted), and sets the route to `completed` only from planned or in-progress.** Those are the states the partial unique indexes treat as busy. *Cost if wrong:* a pending-but-finished assignment would otherwise pin the rider forever.
- **The close predicate uses an expected task count recorded at emit time (migration dispatch `0020`; NULL keeps the legacy stop-count behaviour).** It is data, not an assumption about job shape, so it also survives pickup-only jobs. This replaced the Task 0.12 ruling not to harden the plan's "every stop has a task" predicate, which never protects a real route and could let `PICKUP_COMPLETED` close while the rider still holds the parcel; the final review showed the emitter always emits a delivery leg. *Cost if wrong:* not recorded.
- **`expected_tasks` is recorded atomically in the same INSERT as the assignment, or the emit fails; the runbook gains a pre-flip check that no active pre-0020 quick-dispatch assignment has NULL `expected_tasks` (runbook step 7).** *Cost if wrong:* not recorded.

### Carrier

- **`create_sla_record` refuses when the carrier is missing or its `tenant_id` differs from the record's, before insert, publish and webhook; the internal `POST /v1/internal/sla-records` route binds the tenant to `claims.tenant_id` and returns NotFound on mismatch.** The carrier service owns the carrier table and hub-ops cannot read it. The first version (Task 0.13a) trusted a `tenant_id` from the request body, so the guard did not bind the caller's tenant. The gateway blocks `/v1/internal` and no in-repo caller exists. *Cost if wrong:* one extra lookup per allocation.

### Geocoding and pin

- **With the geocoding flag off, the booking stores quality, source, provider and `geocoded_at`; `place_id` and confidence stay NULL.** Provider name and our own timestamp are not provider result data (spec section 7 limits id, accuracy and confidence). *Cost if wrong:* two harmless columns filled.
- **`home_move` and quote paths not recording quality is acceptable.** They read UNKNOWN, which fails closed (never store-allocated), and home moves are not a store-network product. *Cost if wrong:* not recorded.
- **An address with no or unknown accuracy maps to UNKNOWN; postcode, district, region and country map to LOCALITY.** UNKNOWN is the most conservative reading. *Cost if wrong:* not recorded.
- **A valid pin sets coordinates, `source=customer_pin` and `provider=customer`, but keeps the geocoder's quality; a geocoder failure with a valid pin still applies the pin with quality UNKNOWN.** The pin does not make the address text more precise. The Phase 1 resolver must accept `source=customer_pin` or quality in ROOFTOP, BUILDING, PARCEL. *Cost if wrong:* the Phase 1 resolver must read source, not only quality.
- **An invalid pin is rejected as 422 (`AppError::Validation`), not silently dropped; the pin check runs before the origin geocode.** It is explicit caller input. This corrected the earlier "400" ruling and the contract; code was unchanged. *Cost if wrong:* a client sending (0,0) as "no pin" is rejected; none do today because the fields are new.
- **The optional pin fields (`pin_lat`, `pin_lng`, `building`, `unit`, `area`) were added to the booking address schema in the same commit as Task 0.15.** Task 0.2 was supposed to include them and did not (the schema had only latitude and longitude); contracts come first. *Cost if wrong:* none.
- **`building`, `unit` and `area` length caps are enforced by an explicit character-count check next to the pin check.** Nothing calls `.validate()` on `CreateShipmentCommand` or `AddressInput`, so the `#[validate]` rules are decorative (pre-existing). Whole-command validation is left to the owner. *Cost if wrong:* not recorded.
- **Quote tokens binding the destination was not fixed in Phase 0.** `QuoteTokenPayload` never signs origin or destination, so a quote for address A can already book address B. A pin-distance cap would reject legitimate UAE pins (locality-level geocodes sit kilometres from the door), and binding coordinates into the token is a pricing change for the owner. *Cost if wrong:* distance-priced bookings can be redirected after quoting, which is already true today.

### i18n

- **Reading `NEXT_LOCALE` via `cookies()` in `i18n/request.ts` makes every page dynamically rendered; accepted.** Portals are authenticated and already dynamic; only the landing site's marketing pages lose static rendering. *Cost if wrong:* landing time to first byte; revisit with a static locale for landing if it matters.
- **An Arabic-capable `next/font` (Noto Sans Arabic, Arabic subset) is applied only when `lang=ar`.** Inter and Space Grotesk have no Arabic glyphs. *Cost if wrong:* one extra font file per portal.
- **No locale switcher UI in Phase 0; verification sets `NEXT_LOCALE` directly. `check-i18n-keys.mjs` also compares Android `values` against `values-ar` string names and is wired into `ci-frontend.yml`.** The plan does not ask for a switcher. *Cost if wrong:* one CI step.
- **Frontend typecheck is run after deleting `tsconfig.tsbuildinfo`, landing uses `npx tsc --noEmit` (it has no typecheck script), and the lint gate is "no new eslint Error lines".** `next.config` sets `typescript.ignoreBuildErrors` and `eslint.ignoreDuringBuilds`, so `next build` is not a type or lint gate. *Cost if wrong:* not recorded.
- **Converting the dashboard chrome to RTL is out of Task 0.16's scope (the plan converts the Payouts page only).** *Cost if wrong:* an Arabic store user sees English chrome and a clipped sidebar toggle until the chrome follow-up.

### POD/POP ownership

- **POD initiate, POP initiate and the delivery PIN path all use one rule, `verified_booking`: they need a successful order-intake answer naming the caller's tenant. An outage, a missing `tenant_id` or an unset `ORDER_INTAKE_URL` returns 503; a foreign or missing shipment returns 404, with nothing written. POP billing comes from that same verified answer, and the device-value billing fallback is deleted.** The driver app syncs through `OutboundSyncWorker`, which retries any failure with backoff (capped at 5 minutes, never dropped) and `device_timestamp` is taken at capture, so a 503 delays sync without stopping the courier or losing evidence. Ownership must be decided by the booking record's tenant, never by who wrote a row first. This is the third version: refuse-if-another-tenant-has-a-row was replaced because tenant B could pre-create a row on A's shipment id and block A (squatting); the next version, ownership via order-intake failing open on an outage, was replaced because a foreign row is not inert (pod publishes `PICKUP_CAPTURED` and `POD_CAPTURED`, and order-intake's `status_consumer` transitions shipments by id alone). *Cost if wrong:* during an order-intake outage POD and POP sync stalls until it recovers, and SLA dashboards that read `server_timestamp` lag; evidence and `device_timestamp` are intact.
- **order-intake `GET /v1/internal/shipments/:id/billing` now returns the shipment's `tenant_id`; the POD client compares it and a mismatch is ShipmentNotFound, while a missing field counts as an outage, not a pass.** The endpoint was unscoped (`get_by_id(id)`), so "ownership via order-intake" had only proved existence. `exists_for_other_tenant` was deleted, and the PIN lookup `recipient_phone_for_shipment` is bound to the tenant, closing a pre-existing cross-tenant SMS. *Cost if wrong:* not recorded.
- **`uq_pod_shipment` and `uq_pop_shipment_submitted` became per-tenant unique indexes on `(tenant_id, shipment_id)`, in one migration.** They were unique on `shipment_id` alone, so a foreign row still squatted at the database layer. The change is strictly weaker than today's index so it always builds, and conflict targets are `ON CONFLICT (id)`, so old images keep working during the roll. *Cost if wrong:* not recorded.
- **Internal evidence and POP-status reads take a required `tenant_id` and filter by it; all callers were updated in the same commit, and telemetry `list_for_shipment` is bound to the tenant.** The old reads returned the newest row from any tenant, which allowed cross-tenant evidence poisoning. Images deploy together. *Cost if wrong:* an old caller image without `tenant_id` gets 400 during a rolling restart window.
- **POD by-id reads are scoped by `claims.tenant_id` at the query, with the same NotFound for foreign ids.** Fixed here although pre-existing, because it was a live cross-tenant read of personal data and Phase 0's goal includes closing live exposures. *Cost if wrong:* not recorded.
- **pod read handlers get a partner guard: a pid-bound caller reads only evidence it captured itself (`record.driver_id == claims.user_id`); anything else is NotFound on by-id reads and empty on by-shipment lists. Unscoped callers are unchanged.** POD and POP evidence is a shipment's recipient photos, signature and GPS, and the `--riders` backfill hands pid tokens to riders; the driver app reads its own POD by id and no partner-portal page calls pod. *Cost if wrong:* a pid-bound rider cannot see a POD another rider of the same partner captured on a shared job; no such flow exists today.

### Scope scanner and partner portal

- **The route check (`scripts/check-openapi-routes.py`) was extended in Task 0.4 to also match routes declared relative to a nested `/v1`.** The original only saw literal `/v1` paths and would have missed identity's protected routes; it was mutation-tested again. *Cost if wrong:* not recorded.
- **The partner-scope inventory is plain `path::fn: status  # reason` lines (valid YAML, parsed by regex) so CI needs no PyYAML, and the script also verifies each status against the source (denied must contain `require_unscoped`, scoped a scoping marker) and fails on stale entries.** This is stronger than the plan asked, and detection includes handlers that only call the scoping helpers. *Cost if wrong:* not recorded.
- **The partner Orders page (`apps/partner-portal` `orders/page.tsx`) is read-only and shows real status (Pending, Assigned, Picked Up, In Transit, Delivered, Exception, Unknown); the dispatch roster fetch, assign controls and `MOCK_*` constants were deleted and the KPIs reworked.** The final review found the page always empty. Attempted, partial and piece-exception statuses were then mapped to Exception rather than Unknown. *Cost if wrong:* not recorded; the page was not run against a live partner login.
- **Other partner-portal calls to refused endpoints (driver-ops `/v1/drivers` list, update and register; identity `POST /v1/users` rider invite; manifests) stay out of Phase 0.** The `partner` role holds only `carriers:read`, `carriers:manage_own` and `shipments:read` (`rbac.rs:237`), so these calls were already refused before this branch; this is a pre-existing broken page, not a scope leak. *Cost if wrong:* a carrier cannot manage riders from the partner portal until carrier rider management gets a scoped endpoint (decide whether it reuses the Phase 1 store-rider path).

## 2. Open items for the owner

Each item is marked pre-existing (the problem existed before this branch) or introduced-and-deferred (this branch created it, or its tooling, and left it).

- **Quote token does not bind the destination** (`QuoteTokenPayload` in order-intake). A quote for address A can book address B. Fix direction: bind destination coordinates into the signed token, which is a pricing change. Pre-existing.
- **Whole-command `validate()` is not enforced** on `CreateShipmentCommand` and `AddressInput`; the `#[validate]` rules on `line1`, `city` and `country_code` are decorative. Enforcing it would start rejecting inputs such as `line1` shorter than 5 characters, so it is the owner's call. Pre-existing.
- **hub-ops `upsert_routing_handler`** (`bootstrap.rs:2583`) still stores any `carrier_id` unvalidated; carrier now refuses at allocation time. Pre-existing, partly mitigated by the carrier tenant check.
- **Carrier MCP (Model Context Protocol) tools have no permission checks** (carrier `bootstrap.rs:358-407`). The ledger gave no fix direction. Pre-existing.
- **Carrier `rate_shop` shows every carrier price quote to any `carriers:read` holder, including partners.** Classified not_sensitive in the inventory; it is a product decision. Pre-existing.
- **The scope scanner cannot see handlers that take claims with no permission check** (for example driver-ops get-driver-by-id). Fix direction: needs its own audit. Introduced-and-deferred (a limit of the new scanner; the handlers are pre-existing).
- **RTL dashboard chrome**: `apps/partner-portal/src/app/(dashboard)/layout.tsx` uses physical classes (`left-0`, `ml-3`, `-right-3`), so Arabic users see English chrome and a clipped sidebar toggle. Fix before the Phase 1 Store Workspace. Introduced-and-deferred.
- **Landing `login`, `setup`, `terms` and `privacy` pages have inline Space Grotesk on inner elements**, which will override the Arabic font when those pages are translated. Introduced-and-deferred.
- **admin-portal `/api/pop-status` BFF** takes the tenant from the access cookie's payload without verifying the signature (same as `/api/auth/me`). It returns only completion booleans for shipment ids the caller already knows. Fix: verify the signature or route through the gateway. Pre-existing.
- **order-intake `status_consumer` applies shipment transitions by id without checking the event's tenant** (`TRANSITION_BY_ID_SQL`, and the by-AWBs variant). Fix: bind both to the envelope tenant once every producer is audited to stamp it correctly. Pre-existing.
- **identity `invite_user` returns `temp_password` in the API response** (`users.rs:49`, marked DEV-ONLY TODO). Fix: gate it behind a dev flag before production. Pre-existing.
- **Within a tenant, any merchant or customer token can read any shipment's POD or POP by shipment id** (the merchant-portal `/api/pops` BFF calls `list_pops`). Fix: extend `verified_booking` with merchant and customer ownership; the order-intake billing response already carries `merchant_id`. Pre-existing.
- **admin-portal typecheck error**: `venues/[venueId]/page.tsx` exports `parseLabels`, which Next rejects in a page file (introduced by `ad8c36d5`, #158). Fix: move `parseLabels` out of the page file. Pre-existing.
- **Routes with stops never get `driver_ops.tasks`** (`TASK_ASSIGNED` comes only from quick-dispatch and gig paths), so they free a rider only through `cancel_route`. The ledger records this as a note for the owner. Pre-existing.
- **Partner-portal pages call endpoints the `partner` role is already refused** (driver-ops `/v1/drivers` list, update and register; identity `POST /v1/users` rider invite; manifests). Fix direction: a scoped carrier rider-management endpoint. Pre-existing.
- **The partner-link `EXISTS` query performance is unmeasured.** Run `EXPLAIN` on staging data during rollout. Introduced-and-deferred.
- **`services/identity/tests/integration/mod.rs` does not compile** (11 errors) and needs repair when someone wires it. Pre-existing.
- **Housekeeping for the user**: remove the stray file `D:\tmp_pl_before.txt` (the implementer's lint baseline; a delete was blocked by the safety check) and the scratch container `los-phase0-pg` on `localhost:55432`. Introduced-and-deferred.
- **Task 0.17 (rollout) waits for the owner's go-ahead.** Steps are in `docs/runbooks/neighborhood-phase-0-rollout.md`. Introduced-and-deferred.
- **Task 0.11 minors:** the round-trip test covers only Completed; the unknown-status error log fires per row read on an old image. Introduced-and-deferred.
- **Task 0.12 minors:** a retried `cancel_route` frees the rider but returns 404 (a test locks that in); serde errors are retried 6 times (about 62 seconds), blocking the partition (inherited shape); the test builds a `KafkaProducer` at `localhost:9092`, making connection noise, worse in CI with `RUST_LOG=debug`; `drop_db` runs only on pass, the race test does not force overlap, and a fully-qualified trait call sits in bootstrap. Introduced-and-deferred.
- **Task 0.13 minors:** `fallback_event` does not itself check the window (`handle` does); a test name promises a log it does not assert; `matches!(Auto)` is repeated in hub-ops. Introduced-and-deferred.
- **Task 0.13a minor:** the handler wiring of `ensure_body_tenant` has no handler-level test (the carrier crate has no harness). Introduced-and-deferred.
- **Task 0.14 minors:** no load-save-load regression test for the geocoding columns; the test AWB built from a random `u32` could collide. Introduced-and-deferred.
- **Task 0.15 minors:** origin pin and parts are silently ignored (the contract does not say so); no `create()`-level test of the 422 or the `dest_parts` flow; boundary tests are thin. Introduced-and-deferred.
- **Task 0.16 minors:** Noto Sans Arabic is preloaded for English users in all four apps (consider `preload:false`); the Arabic font only overrides via `body`, `.font-sans` and `.font-heading`; the `request.ts` and globals rules are duplicated byte-identical across four apps; layout indentation; the Payouts page had no physical classes, so the logical-property example is not demonstrated (the chrome follow-up will). Introduced-and-deferred.

## 3. Verification at finish

`cargo check --workspace --all-targets` is clean, and clippy with `-D warnings` is clean on the 14 touched crates. 1338 tests pass, 0 fail, across 57 suites. The database-backed suites were run per fix round against a PostGIS scratch database, including pod `tenant_scope_db` 12/12, pod `partner_evidence_db` 4/4, order-intake `partner_links_db` 9/9, `scope_over_http` 3/3 and `geocoding_quality_db` 3/3. The customer-portal and landing typechecks are clean. Admin-portal has one error that predates this branch, in the venues page. The i18n key check and the partner-scope check (70 handlers) pass.
